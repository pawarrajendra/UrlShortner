# PostgreSQL Schema and Migration Plan

Status: V1 implemented and verified in Phase 1; Phase 2 API transactions/races verified; V2 implemented/verified in Phase 3; V3 implemented/verified in Phase 4. Sources: [Phase 0 contracts](phase0-contracts.md), [architecture](architecture.md), [implementation plan](implementation-plan.md). PostgreSQL is the runtime and integration-test database; The initial executable migration is [V1 SQL](../src/main/resources/db/migration/V1__core_links_and_idempotency.sql). The additive [V2 SQL](../src/main/resources/db/migration/V2__add_link_expiration.sql) preserves V1; the migration target and readiness expectation are now version 3.

## V1 — Core links and idempotency (P1/P2)

| Table / column | Type and nullability | Named constraint / meaning |
| --- | --- | --- |
| `links.id` | UUID, not null | `pk_links` primary key; generated by application |
| `links.code` | varchar(8), not null | `uq_links_code`; `ck_links_code_base62` checks `^[A-Za-z0-9]{8}$`; case-sensitive comparison/collation required |
| `links.destination_url` | varchar(2048), not null | `ck_links_destination_length` checks nonempty; application owns full URL policy |
| `links.created_at` | timestamp(6) with time zone, not null | UTC instant captured for creation |
| `links.disabled_at` | timestamp(6) with time zone, nullable | Irreversible lifecycle marker; do not delete mapping |
| `idempotency_records.key_digest` | char(64), not null | `pk_idempotency_records`; SHA-256 of globally scoped key using the legacy prefix for compatibility |
| `idempotency_records.request_fingerprint` | char(64), not null | Canonical request digest; `ck_idempotency_fingerprint_hex` checks lowercase hex |
| `idempotency_records.link_id` | UUID, not null | `fk_idempotency_link` → links.id, no cascading delete |
| `idempotency_records.created_at` | timestamp(6) with time zone, not null | Replay starts here; expires exactly 24 hours later |

Add `ck_idempotency_key_digest_hex` for key format and `idx_idempotency_created_at` for cleanup. Code uniqueness supplies its lookup index; no redundant code index. UUIDs are application-generated, so this plan needs no UUID-generating database extension.

V1 intentionally has no `expires_at`, event table, custom aliases, synchronous click counter, browser/country fields, or tenancy table. Runtime role has SELECT/INSERT/UPDATE on links and SELECT/INSERT/DELETE on key records for expired-key replacement; key UPDATE is not granted. It must not DELETE retained links or perform schema DDL. Migration role owns DDL; bootstrap role creation is separate from Flyway history.

## V2 — Optional expiry (P3)

Add nullable `links.expires_at` as timestamp(6) with time zone. Add `ck_links_expiry_after_creation`: `expires_at IS NULL OR expires_at > created_at`. Existing records stay null without destructive backfill. Public resolution returns `410` at/after expiry. No expiry index is required for code-based lookups; links are retained rather than purged by expiry.

Accept timestamps to microsecond precision; compare to the creation instant captured once and use that value in INSERT. A link can become expired before its creation response reaches a client. UTC conversion/input range must agree with the API contract; do not let parser/driver rounding silently change boundaries.

## V3 — Observed redirect events (P4)

Implemented migration: [V3 SQL](../src/main/resources/db/migration/V3__redirect_events.sql). V1/V2 are preserved.

| Column | Type and constraint | Meaning |
| --- | --- | --- |
| `redirect_events.id` | UUID, not null; `pk_redirect_events` | One internal attempt ID; repeated insert cannot duplicate it |
| `redirect_events.link_id` | UUID, not null; `fk_redirect_event_link` | Reference retained links.id; no cascading delete |
| `redirect_events.occurred_at` | timestamp(6) with time zone, not null | Resolution observation instant, not worker execution |

Add `idx_redirect_events_link_time` on `(link_id, occurred_at)` and `idx_redirect_events_time` on `(occurred_at)`. No request ID, queue tick, IP, user agent, country, destination, or token is persisted. Workers INSERT in an independent transaction; stats read committed rows. Runtime role needs SELECT/INSERT and DELETE for retention cleanup, not event UPDATE.

Queries include events at the moving retention cutoff and exclude older ones, regardless of cleanup delay. Cleanup deletes strictly older events in bounded transactions. Date range is half-open; UTC bucket total is derived from the same query result.

## Transaction and error boundaries

- Creation attempt inserts link and optional key in one transaction. Only `uq_links_code` triggers code regeneration; retry budget is five total candidate insertion attempts, each with a fresh transaction.
- A key conflict rolls back the candidate, then reads the winner using a fresh transaction. Same fingerprint replays original result; a live different fingerprint returns `409`.
- Expired key records do not extend replay. Use conditional DELETE matching key digest, original creation time and expiry cutoff; PostgreSQL acquires the row lock and rechecks the predicate after concurrent modification. A zero-row delete rolls back and retries in a fresh transaction; stale cleanup cannot delete a newly recreated key. Use current creation time/state predicates when selecting and deleting cleanup batches.
- Disable commits the database mutation before best-effort cache deletion. Failed mutation never emits successful disable.
- Analytics worker commits separately; catch failures around transaction completion. Do not blindly retry unknown outcomes. Foreign-key failure does not become a code collision.
- Every timeout/error must roll back and release resources. Schema/permissions/outage failures are dependency errors, not client collisions.

## Migration execution and acceptance

One non-web migration job validates Flyway history and applies pending files before replicas become ready. App replicas have no DDL credentials and verify expected version. Never mix Hibernate DDL or startup schema.sql with Flyway. Never mutate applied files or auto-repair a checksum mismatch.

| Check | Expected evidence |
| --- | --- |
| Fresh DB | V1 → V2 → V3 applies with constraints/indexes and UTC round trips |
| Brownfield | Apply V1, insert baseline rows, checkpoint, apply V2; identities/destinations preserved and null expiry remains usable |
| Event upgrade | Apply V3 after V2; retained links/keys unchanged; worker FK and indexes function |
| Repeat startup | History validates; no row reset/destructive replay |
| Invalid/interrupted migration | Nonzero runner exit; replicas not ready; inspect state before recovery |
| Roles | Runtime can perform intended DML, cannot modify schema or delete mapping registry |
| Race/rollback | Real PostgreSQL tests establish unique/key conflicts, fresh retries, no orphan candidates |
| Restart | Committed state survives retained volume; no backup/failover claim |

Phase 1 verified fresh V1, UUID/code/FK constraints, UTC microsecond round trips, runtime permission restrictions, safe nonzero checksum-failure exit, repeat migration and persistent-volume restart. Missing/incompatible schema makes readiness fail while liveness remains healthy. See [validation results](validation-results.md). Phase 2 verified code/key uniqueness races, losing-candidate rollback, concurrent expired-key replacement, disable retention and HTTP behavior. Phase 3 verified V1→V2 with old identities/timestamps/destinations/disabling/keys retained, nullable expiry, invalid-expiry constraint enforcement, UTC precision and boundary/replay behavior. Phase 4 verifies event UUID/FK constraints, event role permissions, UTC/retention queries and concurrent bounded cleanup. Interrupted DDL recovery and backup/restore remain unverified.
